# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

Static Pokémon GO PvP team builder, hosted on GitHub Pages from `main` (root). Design and
milestones live in `PLAN.md`.

## Rules

- No build step, no package manager, no runtime dependencies. Every JS file is a plain IIFE that
  attaches to `window`; never use `<script type="module">`, because it breaks under `file://`.
- Layering: `theme.js` → `data.js` → `engine.js` (pure, no DOM, under test) → `app.js` (state, DOM).
  Never reach back up the chain.
- Data comes from a trimmed PvPoke snapshot in `data/*.js` (plus the GBL schedule), generated by
  `scripts/update_data.py` and refreshed daily by `.github/workflows/update-data.yml`, which turns
  warnings (`warn()` in the scripts) into a "Data refresh needs attention" issue via
  `scripts/report_warnings.sh`. Never edit `data/` by hand; change
  the script and re-run it. The site never fetches third-party URLs at runtime.
- Pokémon icons: `img/pokemon/<stem>.webp`, generated by `scripts/update_images.py` (needs Pillow)
  with `data/images.js` mapping species id → stem. Never hand-edit either. If a ranked Pokémon has
  no icon, add its Pokémon GO form name to `OVERRIDES`; never map a form to another form's icon.
  Images are decorative (`alt=""`, the name is always shown) and the page must work without them.
- `js/data.js` exposes `PvpData.gamemaster()` (pokemon, moves, `pokemonById`, `movesById`) and
  `PvpData.rankings(league)` and `PvpData.images()` as promises. Rankings entries are trimmed: `id`, `score`, `roles`
  (lead, closer, switch, charger, attacker, consistency), `moveset`, `wins`/`losses` as
  `[opponentId, rating]`.
- Tests: `node scripts/run-tests.js` (headless) or `tests.html` (source of truth). Add coverage as
  `test(...)` blocks in `js/engine.test.js`; run the suite before every push.
- Simulator changes: re-check agreement with PvPoke's listed wins/losses (1-1 shields) before and
  after with `node scripts/check-agreement.js`, and keep the figures in `PLAN.md` and the README
  current.
- Engine functions take the gamemaster and rankings as arguments; `Engine.createContext` builds a
  league context whose matchup rows are cached, so reuse a context across searches.
- `app.js` builds HTML strings: every value from data goes through `escapeHtml`. Results render
  from `Engine.describeTeam`; keep display wording honest (a "weakness" can still be a win).
- Design context: `PRODUCT.md` (users, purpose, principles) and `DESIGN.md` (the visual system:
  tokens, components, rules). Keep `DESIGN.md` in step with `styles.css` as the design phases in
  `PLAN.md` land.
- `index.html` loads the site's own files with `?v=<date>` (`styles.css`, `js/*.js`). Bump it
  whenever any of them changes, or a browser holding a cached copy can run a new `app.js` against
  an old `engine.js`. `data/` files are left untagged (refreshed daily, and tolerant of a few
  minutes of staleness).
- UI changes: check the page in headless Playwright (installed globally, never in this repo; on
  the user's Mac: `require('/opt/homebrew/lib/node_modules/playwright')`), not
  the user's own Chrome, at desktop and 390px widths, light and dark, over http and `file://`,
  with no console errors.
- State lives in two places: `localStorage` (`pvphelper-state-v1` for the view,
  `pvphelper-ivs-v1` for IVs the viewer typed, per species, `pvphelper-saved-v1` for saved teams,
  each re-validated by `loadSaved`) and the URL hash (`#l=&s=&p=&t=&e=&c=`, see
  `hashFor`/`readHash` in `app.js`; `e=0` means "Use Elite moves" is off, `noElite` in state;
  `c` is the 1-based team compared with the selected one, `compare` in state, cleared whenever
  the selection resets). `pilotHidden` (whether "How to play it" is closed) is saved locally only,
  via `saveLocal()`: the `<details>` toggle event can fire late, so it must never touch the URL. A saved team stores its view's hash and reopens through `hashchange`. A hash on load wins over saved state. Engine contexts are cached per
  league and Elite TM setting (`contextKey`).
  Picks are up to three slots, kept filled-first by `compactPicks`; three picks are the viewer's
  own team (`suggest` returns just that team, and the style doesn't apply). The third field shows
  once two are picked, and each field's list hides the other picks' species and, once one is
  picked, other Megas. `.impeccable/` (critique snapshots) is git-ignored.
  Any new persisted field goes through `applySaved` validation. Team style values are `abc`,
  `pair`, `any`; retired values (`abb`, `aba`) are mapped in `STYLE_ALIASES` so old links work.
- Formats come from `data/formats.js`, built by `update_data.py` from the GO Battle League schedule
  in Pokémon GO's game master (mirrors listed in `GAME_MASTERS`): the open leagues (`great`,
  `ultra`, `master`) always, plus every cup with a week not yet over. The page shows cups live now
  or starting within 7 days, by the viewer's clock, and tags live ones. Nothing else hard-codes a
  cup: the picker, tests, test runner and image script all read `formats.js`. To offer a new GBL
  league, add one line to `GBL_LEAGUES` in `update_data.py` (game league id → site id, name, PvPoke
  cup, CP), matched by hand: names, CP caps and rules don't line up reliably between the game and
  PvPoke. The refresh warns about scheduled leagues missing from the table, and about a schedule
  that is running out. Engine functions take a league id or a CP cap; the app passes the cap.
- Megas are ordinary Pokémon in PvPoke's data (`charizard_mega_y`, tag `mega`), sharing the base
  form's Pokédex number, so the one-per-species rule already covers them. A trainer can have only
  one Mega-Evolved Pokémon at a time, so a team holds at most one Mega or Primal (Primals are
  tagged `mega` too): `isMega` in `engine.js`, enforced in `candidates`, `suggest` (two Mega picks
  are refused with a message) and `bestTeams`. Neither the game master's league rules nor PvPoke's
  data encode this limit; it is the game's general Mega rule. Follow PvPoke for their rules: a Mega's "+" charged move (`isMegaMove`) gets
  `MEGA_BONUS` by Mega level (3, or 4 with tag `supermega`), and supermegas reach level 52. The
  open-league rankings contain no Megas; GBL leagues with `allowTempEvos` are the Mega formats.
- Wrap all `localStorage` access in try/catch, and re-validate persisted fields in `load()`.
- Keep the README's status table and `PLAN.md` milestones current with each milestone. The user
  asked for the README to be kept up to date as the project grows.
- Work on `main`; no feature branches or PRs unless asked. When a change is ready, stop and tell the
  user it is ready to review locally (what changed, how to see it, test results). Commit only
  once they have reviewed it, and push to GitHub only after they give the go-ahead: a push goes
  live on GitHub Pages straight away. Never push on your own initiative.
- If a feature would need something GitHub Pages cannot provide (a server, secrets, server-side
  storage), raise it with the user before building it.
